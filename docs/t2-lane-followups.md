# T2 レーン: 有効化の前に必要なこと（設計メモ）

pals-agent#107 で入れた T2 レーンは、全フラグが既定 off で、本番には配備していません。実際に有効にする前に、次の3つが要ります。

## 1. 使用量の計上の契約（実装済み: 既定値の変更）

- `ProofPipeline.accounting_wait_seconds` の既定は **0** です（以前は15）。答えは、誰も使わない呼び出し（競争の敗者のモデル呼び出し、使われなかった Draft）を待ちません。
- 代わりに呼び出し側は、**答えを公開した後、かつ使用量のスコープが終わる前に** `result.background.drain(timeout)` を呼びます。返り値は、期限までに終わらなかった呼び出しの数で、その使用量はその実行には入りません。0 以外なら警告を出します。
- 評価ランナーは、時計を止めてから回答段階（意味レビューと説明）を実行し、その後で `drain` します。つまり測定した「回答完成」の時間は、この契約を守る呼び出し側が見る時間と同じです。待つ設定（正の値）にすると、答えがその分遅れます。

### 追記（強化）

- 例外で終わった実行でも、`exc.t2_background`（`RunBackground`）に残りの呼び出しを渡す。呼び出し側は、答えを返せなかった場合も `drain` する。投機的な説明・レビューは破棄し、その使用量は通常の報告先に入る。
- 破棄された投機的な呼び出しの使用量は、評価用の受け口（`discarded_usage_scope`）が無い限り、通常の使用量の報告先へ流す（本番の支出が過少に報告されない）。**採用しなかった保持中のハンドル**（答えを出すが採用しない場合）は、`t2_lane.settle_unadopted(handle)` で報告する。採用すれば従来どおり採用時に報告される。

## 2. Lean の同時実行の上限（一部実装、残りは設計）

- 実装済み: `PALS_T2_LEAN_SLOTS`（1競争あたり、既定2）に加え、`PALS_T2_LEAN_PROCESS_SLOTS`（プロセス全体、既定 0 = 上限なし）。`PALS_T2_LEAN_PROCESS_SLOTS` だけを設定すれば（T2 のフラグは全部 off のままでも）、パイプラインの**すべての検証器の呼び出し**（最終コンパイル、Sketch の検査、補題の修復、競争の候補）が `SlottedVerifier` を通ってこのプロセス全体の枠を使います。パイプラインの構築時に読むので、起動前に設定します。枠のセマフォは大きさごとにプロセスで1つです。複数のジョブが同時に走っても、合計のコンパイル数は枠を超えません。キューで待っていて取り消された候補はコンパイルしません。
- 枠の値は、実測した並列コンパイル能力から決めます（「lean-slots」セッションの測定、検証器の枠数の設定）。ここでは決めません。
- 未実装（設計のみ）: **検証器側の取り消し**。すでにコンパイル中の敗者は、今は最後まで走ります（CPU を使い続ける）。案: 検証器の `verify` が、実行ごとの取り消しイベント（`ContextVar` で渡し、既存のラッパーの署名を変えない）を、プロセスの待機ループで確認し、立っていたらプロセスグループを終了する（既存の `_kill_process_group` を使う）。取り消された結果は成功にも失敗にも数えず、`lean.compile_interrupted` 相当の別の結果にする。`lean_verifier/http_server.py` は別のセッションの担当なので触りません。枠の測定結果が出てから、そのセッションと合わせて実装します。

## 3. worker への配線（提案のみ。有効化しない）

別PRで、レビューを受けてから入れます。

| 項目 | 内容 | 注意 |
|---|---|---|
| drain | 答えを公開した後、使用量のスコープが終わる前に `result.background.drain(...)` | 失敗しても答えは変えない |
| 説明の採用 | `_ensure_summary_explanation` の `pregenerated_explanation` で `result.speculative_explanation.adopt(...)` を、既存の speculative 経路と同様に試す | 採用は同じ（命題・ソース・言語）のときだけ。出力レビューと主張は従来どおり |
| 意味レビューの採用 | `result.speculative_review.adopt(...)`。採用しても、承認の決済（settle）は従来どおり | **本番は API 側が検証する `api_reconcile` モードで、レビューは別の配信で走る**。パイプラインの結果のハンドルは、その配信へ持ち越せない。したがって配線できるのはローカル検証モードだけで、本番の分離した配信では採用できない。それを確かめてから、範囲を決める |
| `routine` | 査定の出力に難度の項目が無い（route / rationale / extracted_statement / question、前判定、決定のスキーマを確認した）。最小の追加案: 査定のルート判定のスキーマに真偽値 `routine` を足し、フラグの背後で `run_statement(routine=...)` に渡す | 項目名は査定側の担当と決める。推測で配線しない |
