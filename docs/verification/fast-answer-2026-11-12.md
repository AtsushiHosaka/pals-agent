# 高速回答: モデル時間を削る手の実測 (2026-11-12)

前提: 常駐 Lean([resident-lean-2026-11-12.md](resident-lean-2026-11-12.md))で検証の固定費は 1.3 秒になった。残りはモデルの待ち。ここでは「命題の形式化 + 忠実さの関所 + 回答の表示」の 11〜12 秒を、呼び出しごとに分解し、削る一般的な手を比べた。フラグ・設定はすべて既定 off。このブランチは #120 の上に積んでいる(#120 のマージ後に基底を main へ)。`http_server.py` と審査プロンプト(`explanations.py`)は触っていない。

## 結論

- 自動化 + 1 回の呼び出しで閉じる題では、**回答表示までの中央値 6.2 秒、検証済みまで 4.3 秒**(n=21、最大 11.2 秒)。10 秒以内は 18/21。
- ただし評価した 20 題(新入生 12 + 学部 8)× 2 回のうち**答えられたのは 21/40(52%)**で、答えた 21 件はすべて Lean と既存検証器の監査を通り、命題の忠実さも目で確かめて**誤答は 0**。残り 19/40 は通常経路へ落ち、落ちるまでに中央値 6.0 秒(最大 9.2 秒)を使う。
- **10 秒目標は「全題の中央値」では満たしていない。** 全 40 件のうち 10 秒以内に回答表示まで届いたのは 18 件(45%)。通常経路は同条件で中央値 61 秒(最小 29 秒)。
- 残りの秒数と、何があれば消えるかは「5. 残りと次の手」。

クリティカルパスは「形式化 4.3 s → 往復 2 呼び(逆翻訳 5.2 s + 比較 3.8 s)」で、**形式化 + 関所が 11〜12 秒**になる。Lean はこの経路の 1 割以下。待ち時間は出力トークン数にほぼ比例せず、1 呼び出しあたり 2.5〜4 秒の固定分(推論と API)がある。

**#137 の時計と説明:** #137 は「クリックから回答が表示されるまで」を測り、「回答の先行表示、未検証回答」を速度達成に数えないと書いている。したがって**回答は検証済みの内容と説明を含む**と読み、この文書の「回答表示まで」は説明の生成を含める。説明はひな形(モデルなし)で出せる題では 0 秒、そうでなければモデル呼びが要る(下の高速回答では 2.4 秒)。ただし本文書の高速回答の説明は、既存の「説明の出力レビュー」(`explanations.py` の審査)を**通していない**。審査を直列に足すと約 +2〜5 秒で、中央値は 8〜11 秒になる(未測定、見積もり)。

## 4. 実装(`pals_agent/fast_answer.py`、既定 off、どの経路からも import されない)

- `merged_call`: 1 回で種類・命題・証明(最大 3)・否定の証明(最大 3)を返す。`compute`/`explain` は未対応(通常経路へ)。
- `FastAnswer.run`: N 並列の統合呼び → 到着順に、層 0 の文法、層 1 の許可リスト(常駐の子)、証明の競争(モデルの証明 + portfolio、`find_source_violation` を通らないモデル文は子に渡さない)→ 最初に閉じた命題で、投機的に開始した関所・説明と並行して `LeanVerifier.verify`(方針検査・コンパイル・信頼監査)。**verified は検証器の通過のみ。** 関所が通り、検証済みで、説明が出たときだけ `answered`。`P` と `¬P` が両方閉じたら答えない。
- 例外はすべて `fallthrough`。モデルが失敗しても通常経路に影響しない。
- 実 Lean のテスト 4 件(正しい証明で回答、審査が却下したら回答なし、偽の命題は回答なし、否定の証明で「いいえ」)と純粋部のテスト。

## 6. 限界(正直に)

- n は小さい(20 題 × 2 回、各題の繰り返しは同じ題)。**#137 の条件(公開経路、30 人同時、クリックから表示)の判定ではない。** マシン負荷は 8〜15 で、他セッションと共有。
- 通常経路の 20 題と高速回答の 20 題は同じ題・同じ依頼文・同じ日だが、同時刻の交互実行ではない(通常経路 → 高速回答の順)。
- 探索の途中で held_out の 2 題(`seed-sum_derivative`、`logic_no_negative_natural`)を、最終評価の前の実験(`run_fast_variants.py` の試走と `run_merged_probe.py`)で使ってしまった。最終評価と文書の表からは除いてある。ジャーナルにも書く。
- `terse` の審査文言は、敵対セットの失敗の型を含む(未知の型への検出力は未測定)。`terse2` は往復を使わないので、現行より独立性が弱い。
- 高速回答の説明は既存の説明審査を通していない。
- 評価の題は 1 つの用語で閉じているものが多く、`compute`/`explain` 型は対象外。
- 本番の検証器は Linux・セキュリティ境界つきで、この測定は Mac の常駐 Lean。検証 1 回の時間は Linux で 1.3 秒(前の文書)で、本評価の表は Mac。

## 7. 独立レビュー後の追記(2026-11-13)

- **忠実さ**: 通った 28 組(題 × 命題の形)を目視した。27 は忠実、1 は依頼より弱い(`Fin n` への特化。関所は通したが既存の解説レビューが却下し、表示されなかった)。**関所の誤受理が 1 件あった**ので、前節の「誤答 0」は「関所 + 既存の解説レビューを通って表示された誤答は 0、関所だけでは 1 件の誤受理」に訂正する。全件の表: pals の `docs/improvement-journal/entries/2026-11-13-fast-answer-faithfulness-unseen.md`。
- **初見 24 題**(tuning の未使用分、easy 1・medium 12・hard 11): 既存の解説レビューまで通って答えたのは 4/24(17%)、表示まで 7.9〜10.0 秒。Lean と関所を通ったのは 8/24。調整に使った題の 52% とは別の標本で、難度の分布も違う。
- **既存の解説レビュー**(`explanations.py` の `LeanGroundedOutputReviewer`、編集なし)を `existing_explanation_reviewer` で呼ぶ。解説を既存の形式(overview / sections / conclusion、KaTeX)に合わせないと 9 件中 8 件が却下された。合わせると 5/9 が通り、レビューは中央値 2.7 秒で、**表示は約 +2.7 秒(7.9〜10.0 秒)**。「未レビュー」で出す案: 利点は表示が約 2.7 秒早い。欠点は既存の品質の関所(数式の書式、循環した論証、先取りした要約)を飛ばす。**通常経路と同じ品質を保つなら、通す方を勧める**。
- **関所の一般化**: 審査プロンプトから敵対例の失敗型を外した。単独の審査の誤受理は 0/38 から 2/38 に上がった(旧プロンプトの 0 は例の漏れによる過適合)。`terse2` の関所全体は 57 試行で誤受理 0/57、誤却下 5/57(none)・2/57(low)だが、構造語の表に支えられている。審査が同じモデルの 2 回なので誤りは相関する。`numerals_signal` は使わない。
- **通常経路の同時開始**: `run_with_fallback`(1 つの期限、1 つの使用量台帳)。単体テストのみで、実パイプラインとの結合は未実施。
- **待ちの期限・使用量**: `FastAnswer` の各待ちを `budget_s` で縛った。測定スクリプトの予算 reporter が渡っていなかった不具合を直し、費用を再計算した(各 run 0.02 ドル未満、合計約 0.2 ドル)。
- **起動時の確認**: seccomp(exec の拒否)も実際の子で確かめる。

## 8. 2 回目のレビュー対応(2026-11-13)

- **解説レビューを必須に**: `FastAnswer` は `explain=True` と `explanation_reviewer` が無いと構築できない(`ValueError`)。開発用の抜け道は `allow_unreviewed_explanation=True`(名前で分かる)。却下(`explanation_rejected`)、レビューの失敗(`review_unavailable`)、予算切れ、キャンセルの各経路にテストがある。
- **`run_with_fallback`**: 先に終わった方をすぐ返す(遅い方を待たない)。**二重回答を防ぐ契約**: 公開してよいのは `RaceOutcome.winner` の結果だけ。通常経路が自分で保存する場合は、直前に `claim.try_claim("fallback")` が True のときだけ保存する。速い経路は `answered` かつ `try_claim("fast")` に成功したときだけ勝つ。負けた側は cancel され、公開してはいけない。使用量は `UsageLedger` に、返却後に届く分も記録され、`settle()` の後に完全な合計が読める。
- **テスト**: 各待ちが `budget_s` の残りで切れる(`budget_exhausted`)、使用量が予算に届く、遅れた呼び出しが次の題の記録に混ざらない、の 3 つを、修正を戻すと赤になることを確認した(それぞれ元に戻して失敗を確認)。
- **起動時の自己検査**: メッセージの文字列ではなく、子が作るファイルの有無(自分のディレクトリへの書き込みは成功、他依頼の書き込みと exec は失敗)で判定する。ロケールや Lean の版に依存しない。
- **`seed-composite_injective_implies_first`**: 集合を `Type`(宇宙 0)で書いており、厳密には `Type*` より弱い軽い特殊化。表に注記した。
