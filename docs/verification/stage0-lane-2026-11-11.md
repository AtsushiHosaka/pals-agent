## 1. 忠実さの関所

モデルが書いた命題は、Lean が証明できても、それだけでは出さない。関所は3つの部品で、すべて通らないと出さない。

(a) **2通りの独立な形式化の一致**(指示の違う2回)を Lean で確認する。`P1 ↔ P2` を示すだけでは、真な命題どうしは常に同値なので無意味。そこで、`Iff.rfl`、または仮定を両方向で実際に使った `simpa using` の証明だけを一致とする(証明項で仮定を使ったことを確認)。
(b) **意味審査**(パイプラインの評価の割り当て: Luna、reasoning low)を、証明の試行と並行に走らせる。形式化の途中で、1つ目の命題が出た時点で審査を始める。
(c) **構造語の表**(決定的): 依頼が「斜体」「可換環」「整域」「可換群」「群(可換でない)」を述べるなら、命題がそれに対応する型クラスを含むこと。審査と形式化の2回がそろって `Field` を書いた例(次)を受けて足した表で、**その例に合わせて調整したもの**であり、未知の例での検出力は測っていない。否定(「…は仮定しない」)を理解しないので、否定されやすい語(ハウスドルフ、有限群)は入れていない。
- 数字の被覆検査(自然文の数字が命題にある)は信号として残し、関所にはしない(58題中10題を誤って弾いたため)。

### 敵対的な弱め・変更(テスト専用、`testdata/fidelity-adversarial-v1`、9題。既知の1題+新規8題)

「忠実な命題」と「Lean が証明する弱めた命題」の対で、(a) は弱めた命題と忠実な命題が一致しないこと、(b) は弱めた命題を却下すること、を見る。

| ケース | 種類 | 弱めた命題を Lean が証明 | (a) 一致を拒否 | (b) 審査が却下 | (c) 構造語 |
|---|---|---|---|---|---|
| extra-hypothesis | 仮定の追加(弱い) | する(`positivity`) | ✓ | ✓ | — |
| field-for-division-ring | 構造が弱い(既知の失敗) | する(`exact?`) | ✓ | **✗(承認した)** | ✓ |
| exists-for-forall | ∀ を ∃ に | しない | ✓ | ✓ | — |
| wrong-domain | ℕ と ℝ の取り違え | する(`nlinarith`) | ✓ | ✓ | — |
| off-by-one-bound | 境界の±1 | する(`nlinarith`) | ✓ | ✓ | — |
| special-case | 一般を特殊例に | する(`norm_num`) | ✓ | ✓ | — |
| dropped-membership | 結論が弱い(区間所属の欠落) | しない | ✓ | ✓ | — |
| different-function | 別の関数 | しない | ✓ | ✓ | — |
| commgroup-for-group | 構造が弱い(可換群で群) | する | ✓ | ✓ | ✓ |

- 弱めた命題のうち Lean が証明したのは 9題中6題。(a) は9/9を拒否、(b) は8/9を却下、(c) は 2/2(構造語を含む例)を拒否。
- **(b) の審査は `Field` を `斜体` の依頼で承認した**(3回すべて。reasoning を low、medium、high に上げても同じ)。審査を「構造や型クラスを1つずつ照合する」書き方に直しても変わらない。モデルの限界で、プロンプトでは解決しなかった。
- 忠実な命題の対照: 審査は9題すべて承認、(a) は忠実な命題どうし(同一)で9/9一致。
- 重要な限界: (a) は**2つの形式化が食い違うとき**だけ効く。2つが同じ誤りをそろえて書くと素通りする。`seed-rank_nullity` は2回とも `Field K` を書いた(書き方は違うので、今回の(a) は表面の差で拒否したが、同じ表面なら通る)。この種の誤りを実際に止めたのは (c) の表。

### 形式化した58題で(2通りの形式化、審査、一致)

- 形式化が Lean に通る命題(1つ目)56題。そのうち、モデルなしで証明できたのが22題。
- 証明できた22題のうち: (a) 一致 17、(b) 審査の承認 22(56題すべて承認。審査は実質的に何も却下しなかった)、(c) 構造語 1題を拒否(`seed-rank_nullity`、正しい拒否)、関所を全部通ったのが 17題。
- 偽の却下: (a) が一致を拒否した5題のうち、正しい拒否が1題(`seed-rank_nullity`)、残り4題は忠実な命題(`seed-absolute_value_not_differentiable` など。型クラスの書き方が違う、仮定の置き場所が違う)で、**忠実な22題中の偽の却下は 4/21 ≈ 19%**。(c) の偽の却下は0、審査の偽の却下は0。(a) の偽の却下は、単純化(`simp` による正規化)を強めれば減らせる見込み(未実装)。
- 足した遅延: 証明の後に関所が足す時間は p50 5.2 秒、p90 6.4 秒(審査のモデル呼び出しが支配。1つ目の形式化が出た時点で審査を始めるので、証明と並行)。2回の形式化は並行で、対の p50 4.1 秒、p90 6.5 秒。
- 費用: 形式化2回+審査1回の58題で推計 0.031 ドル。

## 2. 説明のひな形(モデルなし)

`pals_agent/portfolio_explanation.py`。依頼の言語(日本語/英語)に合わせる。ひな形が正直なのは、閉じた手が1つの名指せる事実に対応するとき。

| 閉じた手 | ひな形 | 条件 |
|---|---|---|
| `exact?` | あり: Mathlib の定理名、`#check` の型、docstring、Lean が当てはめた呼び出し | 常に(補題名が取れたとき) |
| `positivity` | あり | 結論が `0 ≤ e`、`0 < e`、`e ≠ 0` の形 |
| `ring`、`field_simp; ring` | あり: 正規形の一致 | 結論が等式 |
| `norm_num` | あり: 数値の評価 | 命題に変数も量化子もない(数値だけ)。`∀ n, ¬ n < 0` のような変数つきは `simp` の補題で閉じるので、なし |
| `decide`、`omega`、`tauto`、`linarith`、`nlinarith` | あり(各手に固定の1文) | 常に |
| `fun_prop`、`continuity`、`measurability` | あり: 和・積・合成の規則 | 結論が連続・微分可能・可測の命題 |
| `simp`、`simp_all`、`aesop`、`grind`、`bound`、`gcongr`、帰納法つき、`constructor` 系 | **なし** | 使う補題が毎回違い、1つの事実で説明できない。モデルが書く説明に回す |

ひな形は、検証に使った規則を述べるだけで、証明方法(ε-δ、帰納法、背理法)の指定や「理由を説明せよ」には応えない。ひな形は最後にそのことを述べる。命題は Lean の記法のまま出る(自然な数式への変換はしていない)。実出力5例は PR の説明にある。

## 3. 段階0の配線

`pals_agent/stage0.py` の `Stage0`(ワーカー、Recipe、モデル呼び出しを注入)と、`ProofReuseRuntime.stage0_input` の1か所のフック(`stage0` が None かフラグ off なら何もしない)。依頼 → (命題が与えられれば使う、なければ2通りの形式化) → 常駐 Lean でポートフォリオ(予算つき) → 関所 → ひな形 → 返す。外れは `fallthrough` を返し、通常のパイプラインがそのまま続く。例外は外に出さない。Draft/Sketch/Prove のコード、`lean_verifier/http_server.py`、説明の審査プロンプトは触っていない。

- 予算の提案(データから): 与えられた命題は 6 秒(答えた15題の最大 4.1 秒)。形式化する場合は 10〜12 秒(答えた11題の最大 9.4 秒。外した題の待ちは最大 15.8 秒で、12 秒の予算でも `exact?` 待ちなどで超える題があった)。10秒の目標を守るなら形式化する場合の予算は 10 秒が上限で、その分、外した題の待ちが最大10秒増える。
- 返す回答の形式(`evidence_kind: lean_portfolio`)を API が受け入れるかは未実装・未検証。フラグを入れても、API の証拠契約が揃うまで本番では使えない。
- ワーカーは本番の検証器ではなく測定用(次)。

## 5. `exact?` の冷起動(原因の確認)

3つの実験(1つの Lean プロセス、`maxHeartbeats` 100000、負荷平均 約12–34)。

| 実験 | `exact?` の所要時間 |
|---|---|
| A: 冷、最初の `exact?` | 約12.8 秒(import 後) |
| B: 無関係な `exact?`(`n ≤ n + 1`)の直後に同じ命題 | 1回目 約15 秒、2回目 **0.08 秒** |
| C: 冷、上限 1000000 | 約13 秒 |
| D: 冷、上限 300000 | 約12 秒 |

**原因: 1プロセスにつき最初の `exact?` で一度だけ Mathlib 全体の補題の探索索引を作るため(約12〜15 秒)。2回目以降は 0.1 秒。** heartbeat の上限では解決しない(上限を10倍にしても時間は同じで、上限内で終わる)。前回の記録の「冷で `exact?` が上限内で失敗する」は、この原因ではなかった: 統合した1ファイルの冷の実行では、`exact?` が**同じファイル内にある先行の失敗した試行の宣言**(`sorryAx` を含む `pals_portfolio_18` など)を「補題」として見つけて当てはめ、`sorryAx` で却下されていた(`[apply] exact pals_portfolio_18 A B C f g h` を確認)。常駐の段階実行は試行ごとに別ファイルなので影響しない。対策: 起動時に1回、無関係な `exact?` で索引を作っておく(約5〜7 秒。ワーカーの再起動のたびに必要)。

## 前段で見つけて直したこと

- ワーカーのタイムアウト後に、前のリクエストの出力を次のリクエストの出力として読む恐れがあった(出力が残る)。タイムアウトや終了ではワーカーを kill して回収し、`alive()` が偽になる。リクエストごとに一意の完了行 `PALS_DONE <path>` を使い、出力の読み取りは `select` と `os.read` の自前の行バッファにした。再現テストを足した(実 Lean)。この欠陥は最初の形式化の通し(1回目)の数字を汚染したので、捨てて測り直した。
